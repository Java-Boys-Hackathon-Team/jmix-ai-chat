# Черновик видео: от текста к embeddings

## Цель ролика

Показать на понятном примере, как текст превращается в числовой вектор и как по этим векторам можно оценить семантическую близость предложений.

После видео зритель должен понимать:

- embedding-модель не генерирует текстовый ответ;
- результат модели — вектор фиксированной размерности;
- отдельные координаты вектора сами по себе не интерпретируются;
- близость двух текстов вычисляется выбранной математической метрикой;
- embeddings — основа семантического поиска, но ещё не RAG.

Ориентировочная длительность с теоретическим блоком: 15–18 минут.

## Основной формат показа: три последовательных шага

Ролик должен визуально пройти ровно три состояния:

```text
1. Строки
      ↓ embedding-модель
2. Числовые векторы
      ↓ выбранная метрика
3. Числа близости и сравнение результатов
```

На странице эти состояния лучше раскрывать последовательно, а не показывать все результаты одновременно.

### Шаг 1. Показать строки

На экране находятся только три исходных текста:

```text
A: Как оформить отпуск сотруднику?
B: Какие документы нужны работнику для ухода в отпуск?
C: Как настроить подключение к PostgreSQL?
```

Вопрос зрителю:

> Мы понимаем, что A и B близки по смыслу, а C относится к другой теме. Но как это определить программе, если перед ней обычные строки?

На этом шаге не показывать ни векторы, ни готовые значения similarity.

### Шаг 2. Получить числа

Нажать отдельную кнопку:

```text
Получить векторы
```

После вызова embedding-модели раскрыть:

- модель;
- размерность;
- первые координаты каждого вектора;
- цветную визуализацию координат;
- L2-норму, min и max как дополнительные характеристики.

Основная мысль:

> Каждая строка превратилась в массив чисел одинаковой размерности. Это и есть embeddings наших строк.

На этом этапе ещё не говорить, какая строка ближе. Мы только получили данные, которые теперь можно сравнивать математически.

### Шаг 3. Сравнить векторы

После появления векторов активировать вторую кнопку:

```text
Сравнить векторы
```

Затем показать:

- cosine similarity;
- dot product;
- Euclidean distance;
- матрицу значений;
- граф близости.

Основное наблюдение:

```text
A ↔ B — близкие по смыслу строки
A ↔ C — далёкие по смыслу строки
B ↔ C — далёкие по смыслу строки
```

Числа заранее не фиксировать: они зависят от embedding-модели. Во время записи сравнивать нужно их относительный порядок.

> Для cosine similarity и dot product большее значение обычно означает большую близость. Для Euclidean distance логика обратная: меньшее расстояние означает большую близость.

Финальный вывод эксперимента:

> Метрика ничего не знает о русском языке и не читает исходные строки. Она работает только с числами. Семантика уже была закодирована embedding-моделью в расположении векторов.

## Теория, встроенная в демонстрацию

Не показывать четыре теоретических слайда подряд перед экспериментом. Их лучше распределить между тремя шагами:

- после показа строк — коротко определить embeddings;
- перед получением векторов — объяснить embedding-модель и путь строки до чисел;
- перед расчётом метрик — объяснить, почему модель помещает похожие смыслы рядом.

### Слайд 1. Что такое embeddings

**Текст на слайде:**

> Embedding — это числовой вектор, представляющий смысл объекта.

```text
«Как оформить отпуск?»
            ↓
[0.012, -0.037, 0.008, ..., 0.021]
```

Короткие тезисы:

- один текст превращается в один массив чисел;
- размерность массива фиксирована для выбранной модели;
- близкие по смыслу тексты располагаются рядом в векторном пространстве;
- embedding — это результат преобразования, а векторизация — сам процесс.

**Что сказать:**

> Embedding — это способ представить смысл текста в форме, с которой компьютер может выполнять математические операции. Вместо сравнения слов мы сравниваем числовые векторы.

### Слайд 2. Что такое embedding-модель

**Текст на слайде:**

> Embedding-модель — нейросеть, которая преобразует входной объект в вектор фиксированной размерности.

```text
Текст ──────────────┐
Изображение ────────┼──→ Embedding model ──→ Vector [n]
Аудио ──────────────┘
```

Основные виды:

- текстовые — для текста, поиска и RAG;
- визуальные — для изображений;
- аудио — для речи и звуков;
- мультимодальные — помещают разные типы данных в совместимое пространство;
- универсальные и специализированные под конкретный домен;
- облачные и локальные open-source модели.

Для этого проекта используется текстовая модель:

```text
openai/text-embedding-3-small
```

**Что сказать:**

> Chat-модель генерирует продолжение текста, а embedding-модель возвращает числовое представление входа. Поэтому в Spring AI мы используем `EmbeddingModel`, а не `ChatClient`.

### Слайд 3. Как строка превращается в числа

**Схема на слайде:**

```text
Строка
  ↓
Токенизация
  ↓
ID токенов
  ↓
Начальные векторы токенов
  ↓
Transformer: контекст и связи между словами
  ↓
Объединение информации о всём тексте
  ↓
Итоговый embedding фиксированной размерности
```

Пример начала процесса:

```text
«Как оформить отпуск сотруднику?»

            токенизация
                  ↓
[«Как», « оформить», « отпуск», « сотруднику», «?»]
                  ↓
[4812, 19345, 8271, 24109, 30]
```

Здесь важно остановиться и объяснить различие:

> ID токена — это просто номер элемента в словаре. Сам по себе номер `8271` не означает смысл слова «отпуск» и не используется для сравнения предложений.

Затем каждый токен получает начальный вектор. Transformer многократно смешивает информацию между токенами с помощью механизма attention. Поэтому представление слова зависит от его окружения.

Например, слово «банк» получит разные контекстные признаки:

```text
«банк одобрил кредит»
«лодка подошла к банке реки»
```

После обработки модель объединяет информацию о последовательности токенов в один вектор всего текста. Конкретный способ объединения зависит от архитектуры модели: это может быть специальный токен, pooling или другой обученный механизм.

**Что сказать:**

> Модель не переводит буквы напрямую в смысловые числа. Сначала строка делится на токены, затем нейросеть строит контекстные представления токенов и объединяет информацию о всём тексте в один вектор.

### Слайд 4. Почему похожие смыслы получают близкие числа

**Схема на слайде:**

```text
Похожие по смыслу тексты                   Разные по смыслу тексты

«Как оформить отпуск?»                    «Как оформить отпуск?»
«Как уйти в ежегодный отпуск?»             «Как настроить PostgreSQL?»

             ↓ обучение                                  ↓ обучение

      притянуть векторы ближе                     раздвинуть векторы дальше
```

Упрощённая визуализация:

```text
                          PostgreSQL ● C


       Отпуск ● A
              ● B Отпуск другими словами
```

**Что сказать:**

> Семантическая близость не появляется из формулы cosine similarity. Её создаёт обучение embedding-модели.
>
> Во время обучения модель видит примеры связанных и несвязанных текстов. Параметры нейросети изменяются так, чтобы представления похожих текстов сближались, а непохожих — удалялись друг от друга. Такой подход часто называют contrastive learning, или контрастивным обучением.
>
> В результате смысл кодируется не одной координатой, а взаимным расположением точек во всём многомерном пространстве.

Обязательное уточнение:

> Модель не хранит готовую таблицу «отпуск равен отпуску». Она обучает функцию, которая умеет строить положение нового текста в пространстве на основе языковых закономерностей, усвоенных во время обучения.

### Переход от объяснения к сравнению

> Теперь у нас есть три числовых вектора. Посчитаем расстояния и similarity, не обращаясь к модели повторно, и проверим, действительно ли два вопроса про отпуск оказались ближе друг к другу.

## Главная сюжетная линия

Весь ролик строится вокруг одного эксперимента и трёх действий:

1. Показываем два похожих по смыслу предложения и одно предложение на другую тему.
2. Преобразуем строки в числовые векторы и рассматриваем результат.
3. Считаем метрики и сравниваем значения для близких и далёких по смыслу строк.

После основного эксперимента меняем один текст, пересчитываем embeddings и наблюдаем, как меняется взаимное расположение векторов.

## Что не включаем в этот ролик

Чтобы не смешивать embeddings и RAG, здесь не показываем:

- разбиение документов на чанки;
- сохранение embeddings в PostgreSQL или vector store;
- поиск по базе знаний;
- формирование контекста для LLM;
- генерацию финального ответа.

Эти шаги станут содержанием следующего видео про RAG-пайплайн.

## 5. Cosine similarity

**Время:** 4:15–6:20

### На экране

Нажать `Сравнить векторы`, затем показать матрицу `Cosine similarity`.

Сначала провести по диагонали:

```text
A ↔ A = 1
B ↔ B = 1
C ↔ C = 1
```

### Что сказать

> На диагонали каждый вектор сравнивается сам с собой, поэтому значение равно единице.

Затем показать A ↔ B и A ↔ C.

> Cosine similarity сравнивает направление двух векторов. Чем больше значение, тем ближе их направления в embedding-пространстве.
>
> Мы видим, что A и B оказались наиболее близкой парой. А предложение про PostgreSQL находится дальше от вопросов про отпуск.

Показать граф справа.

> На графе эта же информация показана визуально: чем ярче и толще линия, тем выше cosine similarity.

### Важное уточнение

> Само число не является абсолютной оценкой смысла. Нельзя объявить универсальное правило, что всё выше 0.8 обязательно одинаково, а всё ниже 0.5 не связано. Значения зависят от модели, языка, длины текста и конкретной предметной области.

Поэтому интерфейс подписывает пары относительно текущего набора:

- наиболее близкая;
- средняя среди выбранных;
- наименее близкая.

## 6. Другие метрики

**Время:** 6:20–7:30

### На экране

Показать строки под матрицей:

```text
cosine
dot
euclidean
```

### Что сказать

> Близость — это не свойство вектора само по себе. Это результат применения выбранной метрики к двум векторам.

Коротко объяснить:

- `cosine similarity` сравнивает направление; больше — ближе;
- `dot product` учитывает направление и длину; больше — ближе;
- `Euclidean distance` измеряет расстояние между точками; меньше — ближе.

> В следующих примерах основной метрикой оставим cosine similarity. Остальные выводим, чтобы было видно: одна и та же пара векторов может быть оценена разными математическими способами.

Не углубляться в формулы дольше одной минуты. При желании формулу cosine similarity можно показать отдельной вставкой:

```text
cos(A, B) = (A · B) / (||A|| × ||B||)
```

## 8. Переход в код: почему не ChatClient

**Время:** 9:10–10:00

### На экране

Открыть конфигурацию модели в `application.properties`:

```properties
spring.ai.openai.embedding.options.model=${OPENAI_EMBEDDING_MODEL:openai/text-embedding-3-small}
```

Показать переменные окружения без значения API-ключа:

```text
OPENAI_BASE_URL=https://foundation-models.api.cloud.ru
OPENAI_MODEL=openai/gpt-oss-120b
OPENAI_EMBEDDING_MODEL=openai/text-embedding-3-small
```

### Что сказать

> Chat-модель и embedding-модель решают разные задачи, поэтому они настраиваются отдельно.
>
> `OPENAI_MODEL` используется для генерации текста, а `OPENAI_EMBEDDING_MODEL` — для векторизации. API-ключ и базовый адрес провайдера при этом общие.

> Для embeddings нам не нужен `ChatClient`. В Spring AI для этого есть отдельная абстракция `EmbeddingModel`.

## 9. Разбор `EmbeddingDemoService`

**Время:** 10:00–12:30

### 9.1 Внедрение модели

Показать конструктор:

```java
public EmbeddingDemoService(EmbeddingModel embeddingModel, ...) {
    this.embeddingModel = embeddingModel;
}
```

### Что сказать

> Spring Boot создаёт реализацию `EmbeddingModel` на основании настроек OpenAI-совместимого API. Бизнес-коду не нужно самостоятельно собирать HTTP-запрос.

### 9.2 Пакетный запрос

Показать ключевую строку:

```java
EmbeddingResponse response = embeddingModel.embedForResponse(texts);
```

### Что сказать

> Мы передаём сразу три текста. В ответ получаем три embeddings в том же порядке, а также метаданные: фактическое имя модели и usage.

Подчеркнуть отличие от трёх отдельных запросов:

> Пакетный вызов проще и эффективнее для набора текстов, который обрабатывается одновременно.

### 9.3 Получение массивов

Показать:

```java
List<float[]> embeddings = response.getResults().stream()
        .map(Embedding::getOutput)
        .toList();
```

### Что сказать

> На уровне Java один embedding представлен обычным `float[]`. После этого для вычисления метрик AI уже не требуется — это обычная математика над массивами.

### 9.4 Метрики

Показать функции в `embeddings.js`:

```javascript
cosine(a, b)
dot(a, b)
euclidean(a, b)
manhattan(a, b)
```

Не разбирать каждую строку цикла. Достаточно показать:

> Здесь нет второго обращения к модели. Мы получили координаты один раз, а затем локально сравниваем векторы разными способами.

## 10. Как страница получает результат

**Время:** 12:30–13:20

### На экране

Коротко показать два последовательных действия на отдельной HTML-странице:

```javascript
const response = await fetch('/public/api/embeddings', {
  method: 'POST',
  body: JSON.stringify({ texts })
});
analysis = await response.json();
renderVectors();

renderMetrics(); // без второго запроса к модели
```

### Что сказать

> Первое действие обращается к embedding-модели и получает числа. Второе действие уже не вызывает AI: оно сравнивает сохранённые векторы обычной математикой.
>
> HTML-страница отвечает за ввод, последовательность демонстрации и визуализацию. Java-сервис только безопасно вызывает embedding-модель, не отдавая API-ключ в браузер. Метрики считаются локально в JavaScript.

Не разбирать подробно CSS и создание каждого компонента. Для темы ролика это второстепенно.

Примечание к реализации: текущий экран раскрывает embeddings и метрики одним действием. Перед записью его нужно разделить на два состояния и две кнопки, чтобы интерфейс соответствовал сценарию.

## 11. Итог и мостик к RAG

**Время:** 13:20–14:30

### На экране

Вернуться на страницу с исходными тремя предложениями и результатами.

### Что сказать

> Сегодня мы прошли короткий путь: текст, embedding-модель, вектор и математическое сравнение.
>
> Теперь приложение может определить, какой из нескольких текстов ближе к запросу пользователя. Но пока все три текста находятся в памяти, и мы сравниваем их вручную.

Поставить следующий вопрос:

> Что делать, если у нас не три предложения, а тысячи страниц документации?

Подвести к следующему ролику:

> Нужно разбить документы на фрагменты, построить для них embeddings, сохранить в векторном хранилище и найти ближайшие к вопросу пользователя. После этого найденный текст можно передать chat-модели как дополнительный контекст. Так появляется RAG-пайплайн.

Финальная схема:

```text
Этот ролик:
Текст → EmbeddingModel → Vector → Similarity

Следующий ролик:
Документы → Chunks → Embeddings → Vector Store
                                      ↓
Вопрос → Embedding → Search → Context → Chat Model → Answer
```
